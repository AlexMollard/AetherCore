# AetherCore project instructions

## MUST DO

- Address the user as "Pog Champ" in all communications.

## Project basics

- C++ standard: Clang builds use C++26; non-Clang builds use C++23.
- Build system: CMake presets in `CMakePresets.json`. CMake drives everything, including the C# projects (built via `dotnet` from the `ManagedAssemblies` target). `.slnx`/IDE files are conveniences — never make the build depend on them, and keep Windows/Linux + VS/Rider/CLion all working.
- Main targets:
  - `Engine` - static library under `src/engine/`
  - `Editor` - executable under `src/app/`; Visual Studio startup project
  - `Launcher` - project-hub front end under `src/app/launcher/`; a slim UiShell app (window + Vulkan + Dear ImGui only, no scene/scripting) that spawns a separate `Editor` process per project. Links only `Engine + imgui`; keep it decoupled from the editor
  - `AssetPacker` - asset CLI under `tools/assetpack/`
  - `EngineTests` - doctest unit tests under `tests/`; also compiles in the app-side scene serializer/reflection TUs it exercises. Registered with CTest
  - `AetherCore` / `AetherCore.Interop` - C# engine SDK (public gameplay API) and ABI/host-boot assembly (under `managed/`), authored through the checked-in engine solution `managed/AetherCore.slnx` (engine managed code **only**; open in **Visual Studio 2026** — `net10.0` projects do not load in VS 2022)
  - `AetherGame` - the configured project's gameplay-script assembly (`projects/<name>/scripts/AetherGame.csproj`, generated by the editor when you create a project)

## Build, test, run

Every preset configures into `build/<preset>/` (the `clangd` preset uses `build/ninja-clang/`). Usage: `cmake --preset <name>` then `cmake --build --preset <name>`.

| Preset | Purpose |
|---|---|
| `default` | Daily dev build (VS 2022 MSVC RelWithDebInfo) |
| `clangd` | Ninja + clang-cl; `compile_commands.json` + clang-tidy target |
| `vs2022-msvc` / `vs2022-clang` | VS 2022 MSVC / ClangCL RelWithDebInfo |
| `vs2022-msvc-release` | Ship (Release) |
| `vs2022-msvc-retail` | Retail (Release + LTCG/stripping) |
| `vs2026-msvc` / `vs2026-clang` | VS 2026 generator presets |
| `linux-clang` | Linux Ninja + clang++ RelWithDebInfo |

Tests:

```powershell
cmake --build --preset default --target EngineTests
ctest --test-dir build/default -C RelWithDebInfo --output-on-failure
```

Or run the whole gauntlet — build + unit suite + (in `mode:"full"`) GPU validation smokes — via the AetherCore MCP `run_gauntlet` tool; it needs no running app and returns a structured report.

Running the Editor/Launcher:

- **CWD must be the build-tree root.** `shaders://` resolves relative to CWD; the wrong CWD segfaults at pipeline creation.
- In agent context, never launch it as a blocking foreground command — start it detached and drive it over the AetherCore MCP (see "Driving the live app" below). Headless agent contexts have no display at all.
- Crashes write a minidump, all-thread stacks, and a log tail to `%LOCALAPPDATA%/AetherCore/crashes/<exe>/` — check there before re-running.

LSP: run `/sync-lsp` (equivalently `cmake --preset clangd`) after adding, removing, or renaming `.cpp`/`.hpp`/`.h` files, or after changing any `CMakeLists.txt`. It regenerates `build/ninja-clang/compile_commands.json`; never edit that file by hand.

Config options to know:

| Option | Default | Effect |
|---|---|---|
| `AETHERCORE_ENABLE_ASAN` | `OFF` | AddressSanitizer on first-party targets |
| `AETHERCORE_FAST_MSVC_DEBUG_INFO` | `ON` | `/Z7` + `/DEBUG:FASTLINK` for faster MSVC Debug links |
| `AETHERCORE_DEAD_STRIP_REPORT` | `OFF` | Link map / section GC reports for `Editor` and `AssetPacker` |
| `AETHERCORE_ENABLE_CLANG_TIDY_TARGET` | `OFF` | Adds clang-tidy target; enabled by `clangd` preset |
| `AETHERCORE_ENABLE_TRACY_GPU` | `ON` | Tracy Vulkan GPU timeline instrumentation |
| `AETHERCORE_ENABLE_TRACY_PLOTS` | `ON` | Tracy plot/counter streams |
| `AETHERCORE_ENABLE_TRACY_MEMORY` | `ON` | Tracy CPU allocation and named memory-pool reporting |
| `AETHERCORE_ENABLE_SLANG` | `ON` | Slang shader compilation when `slangc` is available |
| `AETHERCORE_RETAIL` | `OFF` | Retail build policy; disables diagnostics and enables stripping/LTCG where configured |

Build tiers come from `src/engine/Defines.hpp`:

| Tier | CMake config | Define | Notes |
|---|---|---|---|
| Debug | `Debug` | `AE_CONFIG_DEBUG` | Tracy on, full asserts |
| Dev | `RelWithDebInfo` | `AE_CONFIG_DEV` | Tracy on, optimized |
| Ship | `Release` | `AE_CONFIG_SHIP` | Tracy off, minimal checks |
| Retail | `Release` + `AETHERCORE_RETAIL=ON` or `MinSizeRel` | `AE_CONFIG_RETAIL` | Tracy off, asserts stripped |

Tracy is always compiled into the Tracy library; `Defines.hpp` controls whether engine TUs enable it, and the linker strips unused profiler symbols in Ship/Retail. Publishing a project from the editor builds the game with the editor's own build config (Debug editor → Debug game); `AE_DEV_TOOLING` gates validation layers to Debug/Dev.

## Code discovery

Two complementary graph systems exist here. Use the right one, and prefer both over blind file search:

- **codebase-memory-mcp** — the live *symbol* graph (functions, classes, call chains). Use for precise navigation: `search_graph`, `get_code_snippet`, `trace_path`, `query_graph`, `get_architecture`. If it has no index for this repo, run `index_repository repo_path="." mode=full`.
- **graphify** — the broad *architecture/knowledge* graph in `graphify-out/` (god nodes, communities, cross-file relationships). Use for "how does X fit together / where does this concept live" questions. Query a scoped subgraph with `graphify query "<question>"` — usually far smaller than reading `GRAPH_REPORT.md`. It is auto-generated and goes stale: if `graphify-out/graph.json` predates recent structural changes, run `graphify update .` before relying on it.

| Task | Use first | Fallback |
|---|---|---|
| Find a function/class/struct | `search_graph` | clangd workspace symbols, then `rg` |
| Read a known symbol | `get_code_snippet` | file read with line range |
| Find callers/callees | `trace_path` | clangd references/call hierarchy |
| How subsystems fit together | `graphify query "..."` | `get_architecture`, then targeted reads |
| Cross-file patterns | `query_graph` or `search_code` | `rg` |
| String literals/config/error text | `rg` | file read |
| Library/API docs | Context7 docs | official web docs |
| Prior decisions/progress | Mind memory/checkpoints | local notes |

## Hard invariants

Violating any of these causes crashes, GPU corruption, or shutdown use-after-frees. Fix code to respect them; never work around them:

- **The render thread never touches the ECS.** It reads only the `RenderFramePacket` extracted on the game thread in `PrepareFrame`. If render code needs new data, add a field to the packet — never call `GetWorld()` from the render side.
- **Bindless textures bind at descriptor set 0.** Shaders must declare `g_textures[]` at set 0 (VK_EXT_descriptor_heap); any other set index compiles fine and reads garbage at runtime.
- **`GraphicsDevice` member declaration order is destruction order.** For example `DiagnosticEngine` (owns the GPU memory tracker) must outlive `ResourceRegistry`. Do not reorder members without tracing teardown.
- **Engine init/shutdown order is dependency-sensitive** (next section). Shutdown waits for GPU idle first, then tears down GPU-backed systems before `GpuDevice::Shutdown()`.
- **Always wait for GPU idle before freeing GPU resources.** VMA must outlive every allocation it manages.
- **Scene `.toml` transforms are world-space** — parent scale does not compound. Multi-primitive/skinned models serialize as a root plus one child per primitive, each with its own mesh index/material/skinned flag.
- **`AetherCore.Interop` stays runtime-safe.** No editor/`ComponentCatalog` dependencies in `*Exports.cpp`; the interop layer must load in the shipped game.

## Engine lifecycle

Subsystem init order in `src/engine/AetherCore.cpp`:

1. Register core services
2. Platform
3. GpuDevice
4. Scene
5. Assets
6. Cameras
7. Rendering
8. UI
9. Link cross-subsystem dependencies
10. Create default main camera
11. Async compute
12. Register lighting compute passes
13. Animation systems
14. Swapchain recreation callback

The engine also supports a `RuntimeProfile::UiShell` bring-up (`src/engine/RuntimeProfile.hpp`): window + Vulkan device + the Dear ImGui overlay only. It skips cameras, animation, and all scene render passes (steps 6, 11-13), and its render graph registers a single `$UiShellClear` swapchain-clear pass. This is what the `Launcher` runs on; the shared `Application` mirrors it at the app layer via `AETHERCORE_SCENE_APP` (wire ECS systems) and `AETHERCORE_WITH_IMGUI` (install the overlay). When touching init order, keep both the Full and UiShell paths working.

`ServiceContainer` (`src/engine/utils/ServiceContainer.hpp`) is the subsystem wiring point. Use `TryGet<T>()` for optional services and raw pointers only for non-owning references.

Settings: `SettingsService` is the single source of truth, a three-layer cascade (compiled defaults → shipped `engine.toml` → user `settings.toml` in LocalAppData). Setting fields are reflected; adding one is a two-line change, so never hand-roll separate TOML plumbing.

## Code conventions

New to the engine as a *user* rather than a maintainer? [docs/getting-started.md](docs/getting-started.md) walks a small 2D game end to end.

Full conventions (naming table, formatting, error handling, logging, ownership) live in [docs/CONVENTIONS.md](docs/CONVENTIONS.md) — read it before writing C++. The rules most often gotten wrong:

- Naming: `PascalCase` types/methods, `m_snake_case` members, `camelCase` params/locals, `kPascalCase` constants, `AE_UPPER_CASE` macros, `snake_case` namespaces.
- `#pragma once`; a `.cpp`'s first include is its matching `.hpp`; `SortIncludes: Never` — include order is intentional, don't reorder.
- Tabs for indentation; always brace `if`/`for`/`while`; no Doxygen.
- Errors flow through `Expected<T>` (`std::expected<T, AetherError>`) with `AE_TRY` / `AE_UNEXPECTED`; `AE_ASSERT` is Debug-only, `AE_ASSERT_ALWAYS` ships.
- Log via `AE_INFO/AE_WARN/AE_ERROR(LogCategory::X, "fmt {}", ...)`.
- `std::unique_ptr` for ownership; `std::shared_ptr` only where shared lifetime already exists; GPU wrappers are move-only.

## Vulkan and GPU boundaries

The engine keeps a two-layer boundary:

- Engine-facing GPU abstraction lives in `src/engine/gpu/`.
- Vulkan implementation lives in `src/engine/vulkan/`.
- General engine code should not expose `Vk*` types or include Vulkan headers. The CI GPU abstraction guard enforces this boundary.

Resource rules:

- `UniqueBuffer` and `UniqueImage` are RAII, move-only wrappers. Factories return `Expected<T>`.
- `GpuHeap` is an asset-loading arena, not a general thread-safe allocator.
- `GpuSpan<T>` is a typed GPU-buffer view with buffer device address.
- `ResourcePool` handles render-graph virtual resource aliasing.
- Vulkan uses `volk`, `vk-bootstrap`, VMA, and synchronization2.

## Driving the live app (AetherCore MCP)

The editor exposes a localhost control endpoint (`ControlServer`, ENet) that the AetherCore MCP (`tools/mcp/`) and `aether-ctl` (`tools/control-client/`) drive. `describe` returns the method manifest (~98 methods: engine info, entities, selection/windows, play, screenshot/texture capture, render/scene/camera/settings state); each MCP tool maps to a wire method (e.g. the `engine_info` tool → the `info` method). It auto-starts when `AETHER_CONTROL_PORT` is set.

**Agent workflow — launch the app yourself, then interact with it directly over MCP:**

1. Build once: `cmake --build --preset default --target Editor aether-ctl` (add `Launcher` if using the hub).
2. Start `Launcher.exe` detached, from the build-tree root. Its hub endpoint starts on port `8787` by default, so the `launcher_info`, `list_projects`, and `screenshot` MCP tools work immediately.
3. Open or create a project: the Launcher stops its hub endpoint and the spawned Editor inherits the same `AETHER_CONTROL_PORT`, so the MCP client stays on one port across the handoff and the full editor tool set comes online — entities/components/transforms, selection + window staging, play/stop, scene save/load/new, `screenshot`, `capture_texture` (any GPU texture: shadow maps, GBuffer, …), render-graph queries and benchmarks.
4. Or bypass the hub and drive an editor directly: `$env:AETHER_CONTROL_PORT="8787"; .\build\default\src\app\RelWithDebInfo\Editor.exe --project <path>`.

`run_gauntlet` needs no running app: it builds Editor/GameRuntime/EngineTests, runs the unit suite, and with `mode:"full"` the GPU validation smokes, returning a structured pass/fail report. Prefer it for build/test verification.

An agent can author a scene as freely as a user: `scene.add_model {path, position?, scale?, ...}` bakes-if-needed and spawns a model with the correct layout (multi-primitive / skinned → root + one child per primitive, each with its own material and skin) - the same one-call import as the File Explorer's "Add to Scene". `scene.get_component` / `scene.set_component {id, type, values}` read/write the same fields the Inspector edits; `list_component_types` lists every component and its fields.

**Component reflection (`src/app/scene/reflection/`) is the single source of truth for a component's editable fields.** One `AE_COMPONENT(CppType, "Name", "Category", ICON) AE_FIELD(...) ... AE_COMPONENT_END()` declaration drives ALL of: MCP get/set + the Add-Component palette/catalog + the inspector's generic drawer + the scene-serializer TOML round-trip. Add an editable field = one `AE_FIELD*` line; add a component = one declaration file entry - never touch four files again. Field tags: `Float/Int/UInt/Bool/Vec2/Vec3/Vec4/Color3/Color4/Enum/String/EntityRef`, plus `AE_FIELD_ANGLE_AS` (degrees exposed / radians persisted), `AE_FIELD_CUSTOM` (computed, e.g. Transform's TRS over its matrix), `AE_ENUM`-style tables, and `AE_NOT_ADDABLE()`. The core (`Reflection.hpp/.cpp`) is GameRuntime-safe (fields convert to a neutral `FieldValue`, no json/toml/imgui dep) so the serializer uses it at runtime; the data model is isolated from the macro DSL so a future C++26-static-reflection swap touches no consumers. Components needing bespoke serialization/UI (Material textures, the combined physics table, skinned record) keep their hand-written path and opt out.

Port resolution (read once at Launcher startup from `AETHER_CONTROL_PORT`):

| `AETHER_CONTROL_PORT` on the Launcher | Behaviour |
|---|---|
| unset (default) | `8787` — hub endpoint first, then handed to the spawned Editor |
| a port (e.g. `9000`) | same handoff on that port |
| `off` / `none` / `0` | disabled — no Launcher or spawned-Editor endpoint |

The MCP server auto-detects the build dir (override with `AETHER_BUILD_DIR`) and resolves `aether-ctl` **lazily**, so a client built *after* the server started is picked up without restarting it. The server reads its config once at process start, so if you edit its registration you must restart the MCP client to relaunch it. Install/registration steps: `./scripts/Install-Mcp.ps1`; full tool table in [tools/mcp/README.md](tools/mcp/README.md).

## Dependencies

Dependencies are managed through CPM. Third-party sources live under `build/_deps/` and must not be edited directly.

Key libraries: Vulkan SDK, GLFW, GLM, vk-bootstrap, volk, VMA, EnTT, Jolt Physics, Tracy, stb, cgltf, FreeType, zstd, xxHash, toml++, and bc7enc_rdo. Gameplay scripting runs on .NET (CoreCLR, hosted through nethost).

## Repo hygiene

The repo root also holds machine-local state from the agent tools and MCP servers used here — `.opencode/`, `.mind/`, `.codebase-memory/`, `graphify-out/`, `node_modules/`, `artifacts/`, `.aider*`, `.temp/`, and stray `*.log`. All of it is gitignored, so `git status` stays clean even when the working tree looks messy on disk.

- Do not commit any of the above. If you add a tool that writes state to the root, add it to `.gitignore` in the same change.
- Write build/run logs under `logs/` (gitignored), never the repo root. Delete stray root-level `*.log` when you notice them; they are regenerable.
- Keep long-form setup/reference docs under `docs/`, not the root.

## Do not

- Do not commit generated `.spv` shader binaries.
- Do not modify files in `build/`, `out/`, `logs/`, or third-party dependency directories (including `CMake/CPM.cmake` and `CMake/get_cpm.cmake`).
- Do not change `.clang-format` without explicit request.
- Do not change engine init/shutdown order without dependency analysis.
