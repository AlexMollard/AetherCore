What survives a C# reload?

A collectible C# assembly makes replacing gameplay code possible without restarting the editor. It does not make a running object graph automatically transferable to the next assembly.

A boundary with one shared type identity

Project scripts live in AetherGame and derive from the public AetherCore SDK’s EntityScript. The native host boots AetherCore.Interop, which exposes unmanaged entry points for loading scripts and managing instances. Native code holds handles; the managed registry creates and binds objects to entity IDs. Game authors use the SDK rather than the host’s ABI as their everyday interface.

The game assembly is loaded in a collectible AssemblyLoadContext. Its resolver loads game dependencies from the project’s dependency manifest, but returns the host’s already-loaded SDK assembly for AetherCore. That shared identity matters: a second SDK copy would make an apparently identical EntityScript a different runtime type, undermining discovery and casting. See the load context and resolver.

Build first, replace second

The editor’s reload path rebuilds the project before invalidating existing instances. A compile failure is reported and returns before teardown, so the previous loaded scripts are not discarded merely because the new source did not compile. After a successful build, the system destroys the old instances, clears their handles and requests a fresh assembly load. This is assembly replacement, not an edit to existing objects.

  1. Rebuild: Compile project scripts; stop on a build error.
  2. Invalidate: Destroy old script instances and clear native handles.
  3. Replace: Clear managed roots, request unload, then load the new assembly.
  4. Recreate: Apply cached script properties to new instances before attachment.

This is the editor reload path, not a promise that arbitrary live state migrates.

On desktop, the registry reads the DLL and optional PDB into streams instead of loading the game DLL directly from its path. Windows can then overwrite the file on the next build. The tradeoff is explicit lifetime management: registry tables and the live-instance table are cleared before Unload() is requested. Unloading depends on references being released, not an instantaneous guarantee. The reload ordering and registry implementation show the two sides.

The important Play-mode qualification

The current editor path accepts reload requests outside Play. A request made while Play is running is cleared with a “Stop first” diagnostic, rather than queued for later. This keeps a reload from firing as a surprise when the simulation stops.

The implementation explains the constraint: recreating scripts loses instance-local caches, such as a camera child resolved once during attachment. A running simulation can appear intact while a new script instance no longer has the references it depended on.

The guard avoids a disruptive transition mid-Play; it does not solve general state migration. Read the Play guard and its rationale.

What comes back—and what does not

Script entries remain in the world when handles are invalidated. When an instance is created again, the system copies the entry’s cached properties into it and calls attach. The documented inspector fields are serialized with the entity; these stored values are the supported bridge across instance replacement, not a snapshot of every managed object. The system also has an explicit operation to copy live property values into the cache, but invalidation itself does not perform that copy. Do not assume every runtime field change is captured by reload.

Private caches, object references and other transient instance state are not carried over as an object graph. Constructors and attachment run on new instances, so initialization must tolerate recreation. The registry separately remembers editor tool-window visibility by title using strings in the stable boot assembly; that narrow exception is not general script-state persistence. Read property synchronization, instance recreation, and registry teardown.

Failure is not one transaction

Compile failure occurs before invalidation, but an assembly load failure occurs after teardown has started. The managed loader reports exceptions and returns a negative result; the native subsystem resets its gameplay host without the API on failure. It increments the reload generation on both success and failure, allowing consumers of cached reflection data to discard stale tables. There is no basis here to promise automatic rollback to the prior assembly after a failed load.

If a script type cannot be instantiated, the system retains its fields and disables that failed type until reload. These distinctions make diagnostics and recovery part of the workflow: repair the source or load problem and rebuild, rather than assuming a failed replacement was invisible. See managed load errors, host reset and generation, and instance failure handling.

Same gameplay idea, different iteration paths

Rust gameplay uses rebuild and relaunch rather than the C# F5 path; a fresh process does not migrate arbitrary live state. Browser C# is a separate deployment configuration: prebuilt gameplay runs under the Mono WebAssembly interpreter alongside the native engine, sharing its C ABI. Desktop hostfxr and collectible assembly unloading are absent there; browser changes require rebuilding and republishing.

The browser bridge is a scoped SDK subset, not desktop parity. For example, external native imports, networking and editor tools are rejected in preflight. Keeping these paths distinct avoids presenting an editor convenience as a universal language or platform guarantee. See Rust iteration and C# browser support.
