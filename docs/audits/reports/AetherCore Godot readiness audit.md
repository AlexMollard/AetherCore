# Close failure paths before widening AetherCore

Pog Champ, **AetherCore needs stronger failure handling, complete release gates and a demonstrated support contract before it can support the same production-confidence claim as Godot**. It already contains substantial engine, editor, asset, scripting and export infrastructure; the next investment should make those existing paths dependable. This audit found one freshly reproduced strict-Clang blocker, a conditional renderer deadlock/inconsistent-state path, three data-integrity defects, and several release qualification gaps. The previous six reliability defects and mandatory host-image-copy requirement are fixed baseline work, not open findings here. A narrow, dependable Windows-first product is a realistic engineering objective without reproducing Godot's platform and renderer breadth. Reaching comparable breadth is a separate product program, and neither objective can honestly be expressed as a readiness percentage.

### R1 requires a transaction or a controlled fatal policy

The real managed path is `Animation.Compile` → native export → `RunExclusive(Drain)` → compiler → `AppendAnimations`. `RunExclusive` sets reload/park state, waits for GPU idle, invokes the mutation and restores state only on normal return. Append first extends CPU arrays, relinquishes the old GPU heap and creates/uploads its replacement. Device allocation, virtual-block creation or staging upload can throw. `SafeExport` catches and logs that exception, then returns to the script without restoring the exclusive state. The render thread cannot pass the reload wait; producers subsequently wait for completion or channel capacity. ([Managed API](C:/Users/alexm/source/repos/AetherCore/managed/AetherCore/Animation.cs:25), [native export](C:/Users/alexm/source/repos/AetherCore/src/app/scripting/interop/AnimationExports.cpp:90), [exclusive mutation](C:/Users/alexm/source/repos/AetherCore/src/engine/AetherCore.cpp:316), [database replacement](C:/Users/alexm/source/repos/AetherCore/src/engine/animation/AnimationDatabase.cpp:446), [heap failure](C:/Users/alexm/source/repos/AetherCore/src/engine/vulkan/GpuHeap.cpp:71), [exception containment](C:/Users/alexm/source/repos/AetherCore/src/app/scripting/interop/InteropCommon.hpp:120), [reload wait](C:/Users/alexm/source/repos/AetherCore/src/engine/rendering/RenderThreadState.hpp:45))

**Unpausing alone is unsafe:** the previous GPU state has already been retired and is not a retained rollback state, even if physical destruction is deferred. Build replacement CPU/GPU state separately, commit after successful upload and restore exclusive flags on every recoverable exit. If recovery cannot preserve usable state, enter a controlled fatal/shutdown path that wakes waiters. Acceptance must inject all three failures through the actual script export and verify either intact previous animation or safe termination, with no retired-address consumption. This is a conditional exception-enabled native defect, not a freshly reproduced hang; successful normal compilation and explicit shutdown remain counterevidence. The separate browser path is outside this claim.

### The compiler blocker is reproduced; the data defects are source-proven

Clang-cl 22.1.5 fails four syntax-only probes using the configured command flags because `Throw` omits `LogCategory::Audio`. A default switch arm does not suppress `-Wswitch-enum`. The warning was not demoted in the strict probes. Add an intentional Audio classification, then pass strict probes and full supported compiler builds. Linux shares the warning policy but was not executed here. ([Switch](C:/Users/alexm/source/repos/AetherCore/src/engine/utils/Expected.hpp:106), [configured flags](C:/Users/alexm/source/repos/AetherCore/CMake/TargetDefaults.cmake:28), [strict diagnostic log](C:/Users/alexm/source/repos/AetherCore/logs/godot-product-clang-strict.log:1))

D3 is distinct from the already-fixed ordinary save path. Restore parses recovery first, then calls the truncating writer on the saved scene. A successful open followed by write/close failure or interruption can leave partial destination content. The recovery source remains physically present; it is not sole-copy loss. However, discovery compares mtimes before content, so a failed restore advancing scene mtime can hide the older recovery offer after restart. Use atomic replacement and test open/write/flush/replace faults, source retention and next-open discovery. No power-cut or disk-full reproduction was performed. ([Restore](C:/Users/alexm/source/repos/AetherCore/src/editor/editor/AutosaveRecovery.cpp:209), [writer](C:/Users/alexm/source/repos/AetherCore/src/engine/io/FileUtil.cpp:232), [discovery](C:/Users/alexm/source/repos/AetherCore/src/editor/editor/AutosaveRecovery.cpp:173))

D1 freshness checks mesh magic/version, header readability and source/existing-dependency mtimes, but not the full body or companion inventory. Deleting `.skel`, `.animset` or generated material can leave the cache reported current; runtime then degrades or rejects data rather than repairing it. D2 derives generated material identity from directory plus material name, allowing different models to share and overwrite a path; editor/single-bake warnings exist, but bake-all drops them. Require content/dependency fingerprints, importer/settings identity, complete output validation and unambiguous generated names or explicit collision failure. Test companion deletion, body truncation, preserved-mtime changes and red/blue same-name materials in both bake orders. ([Cache](C:/Users/alexm/source/repos/AetherCore/tools/assetpack/BakeAll.cpp:85), [editor cache](C:/Users/alexm/source/repos/AetherCore/src/editor/editor/ModelBake.cpp:78), [material identity](C:/Users/alexm/source/repos/AetherCore/tools/assetpack/MeshProcessor.cpp:600), [overwrite warning](C:/Users/alexm/source/repos/AetherCore/tools/assetpack/BakeOutputs.cpp:83), [lost batch warning](C:/Users/alexm/source/repos/AetherCore/tools/assetpack/BakeAll.cpp:122))

**Native publication materially mitigates both D1 and D2:** with readable source inputs, PakWriter freshly cooks models, prefers generated output over stale raw cache, and rejects unequal same-priority path collisions. Therefore these findings do not establish silent desktop shipping of whichever material baked last. The `webgpu-3d-v1` route skips source models when a sibling mesh exists and retains the cache risk. Browser preflight can catch startup-visible damage; no defective browser export/render was executed here. Preserve intentional identical-content sharing and authored overrides when fixing identity. ([Fresh cook and priority](C:/Users/alexm/source/repos/AetherCore/tools/assetpack/PakWriter.cpp:75), [Web 3D exception](C:/Users/alexm/source/repos/AetherCore/tools/assetpack/PakWriter.cpp:92), [collision rejection](C:/Users/alexm/source/repos/AetherCore/tools/assetpack/PakWriter.cpp:220), [existing identity tests](C:/Users/alexm/source/repos/AetherCore/tests/assetpack/ModelIdentityTests.cpp:44))

### Physics and networking need declared operating envelopes

R2 discards Jolt Update's error bitfield. Pinned Jolt 5.5.0 reports dropped contacts when pair/manifold/constraint admission fails, and also asserts before returning errors in assertion-enabled builds. Consequently this is **not always silent**: the missed shipping status/policy remains, but exact assert behavior depends on configuration. Native body/pair budgets are 64,536, browser bodies 8,192/pairs 16,384, with 10,240 contacts. Surface rate-limited diagnostics and define continue/degrade/reject behavior; test each saturation error separately. No dropped contacts were observed in this audit. ([Step and limits](C:/Users/alexm/source/repos/AetherCore/src/engine/physics/PhysicsSystem.cpp:572), [discarded return](C:/Users/alexm/source/repos/AetherCore/src/engine/physics/PhysicsSystem.cpp:713), [pinned Jolt errors](https://raw.githubusercontent.com/jrouwe/JoltPhysics/v5.5.0/Jolt/Physics/EPhysicsUpdateError.h), [Jolt assertion](https://raw.githubusercontent.com/jrouwe/JoltPhysics/v5.5.0/Jolt/Physics/PhysicsSystem.cpp))

R3's 10 MiB arena calls `abort` if exhausted, on native and browser. That mechanism is proven; no admitted scene reaching it is established. Measure high-water use under active bodies, joints, CCD and characters, then size/configure the arena or enforce a supported content envelope. Unlimited allocation fallback is not automatically safer. Godot's configurable Jolt temporary buffer is an example of an operating control, not a guarantee against exhaustion. ([Allocator selection](C:/Users/alexm/source/repos/AetherCore/src/engine/physics/PhysicsSystem.cpp:554), [Jolt allocator](https://raw.githubusercontent.com/jrouwe/JoltPhysics/v5.5.0/Jolt/Core/TempAllocator.h), [Godot Jolt memory](https://docs.godotengine.org/en/4.7/tutorials/physics/using_jolt_physics.html#memory-usage))

R4's ENet loop drains deliverable events and copies accepted payloads with no aggregate per-Poll work cap. Individual 64 KiB rejection and waiting-data bounds exist; neither proves bounded frame work. Add measured packet/byte/time budgets, per-peer quotas and bounded queues before a public multiplayer promise, or scope the first supported release to offline/trusted play. No flood, OOM or starvation was reproduced. The editor control endpoint is a separate loopback-only service with request/queue limits, not a publicly bound remote endpoint; its remaining issue is an explicit trusted-local-process policy and optional authentication hardening. ## Godot sets a maturity benchmark rather than a mandatory feature checklist

Godot documents renderer/platform requirements, import contracts, export prerequisites and version maintenance. Those published contracts make it easier to determine what a supported production workflow means. They do not make Godot bug-free: its thread-safety and physics documentation explicitly describe limitations, and its release policy acknowledges upgrade risks. AetherCore should match the clarity and evidence appropriate to its own chosen scope. ([Godot release policy](https://docs.godotengine.org/en/4.7/about/release_policy.html), [thread limitations](https://docs.godotengine.org/en/4.7/tutorials/performance/thread_safe_apis.html), [physics limitations](https://docs.godotengine.org/en/4.7/tutorials/physics/troubleshooting_physics_issues.html))

| Area | Godot 4.7 baseline | AetherCore current position | Needed production result |
|---|---|---|---|
| Hardware/rendering | Forward+, Mobile and Compatibility, multiple graphics drivers and documented fallbacks | Vulkan 1.4, shader objects, EDS3, descriptor heap **or buffer**; host copy optional | Publish and qualify actual GPU/driver contract; older-GPU backend only if product requires it |
| Assets | Content-based reimport, per-asset configuration, ResourceUID | UID catalog, migrations, reflected formats; D1/D2 incomplete cache/identity cases | Complete deterministic outputs and verified references across rename/reimport/export |
| Authoring trust | Established editor workflows; no universal crash-safe save guarantee | Undo/autosave/atomic normal saves implemented; D3 restore gap | Fault-tested save/recovery and mutating-operation coverage |
| Languages/Web | Godot 4 C# Web export unsupported; WebGL2 Compatibility, no WebGPU | C#/Rust WebGPU and bounded 2D/3D profiles exist | Qualify documented language/profile/browser combinations, dynamic branches and toolchain |
| Tests/releases | Documented native tests and sanitizer workflows | Strong retained Debug evidence; other registered suites pass but gates omit them | Complete manual inventory, shipping configs, graceful exit, soak and sanitizer evidence |
| Distribution | Export presets/templates and prerequisites documented | Transactional native publishing, installer/ZIP, payload checks | Execute delivered bytes on clean standard-user machines without developer fallbacks |
| Maintenance/adoption | Public engine license, notices and release/security policy | API/format instability disclosed; aggregate terms/notices and broad maintenance contract unestablished | Owner chooses terms, supported versions, migrations, private report path and release identity |

## Product ownership and explicit unknowns determine the honest release claim

Before public distribution, establish engine terms and complete payload notices. Some project credits and asset license files already exist; the gap is that inspected engine payload rules do not establish root engine terms and an aggregate dependency-notice inventory. This is an owner/legal decision and verification task, not a finding of infringement or permission. Godot's published licensing guidance provides a useful disclosure benchmark. ([Payload list](C:/Users/alexm/source/repos/AetherCore/src/app/CMakeLists.txt:512), [existing credits guidance](C:/Users/alexm/source/repos/AetherCore/docs/web-export.md:191), [Godot licensing](https://godotengine.org/license/))

The inspected release path also lacks recorded checksum/provenance/SBOM generation and signing integration. Decide signing explicitly; record exact tool/runtime versions, artifact hashes and retained symbols, including CoreCLR interop crash diagnostics. A pinned managed SDK already exists, but mutable Vulkan/Inno Setup inputs and .NET runtime channel reduce reproducibility. No external release artifact was inspected for actual signature status. Define supported stable versions, backports, migration expectations and a private vulnerability-report route; existing multiplayer security documentation does not replace a maintained-product policy. ([Release inputs](C:/Users/alexm/source/repos/AetherCore/.github/workflows/release.yml:59), [runtime channel](C:/Users/alexm/source/repos/AetherCore/.github/workflows/release.yml:120), [installer](C:/Users/alexm/source/repos/AetherCore/packaging/AetherCore.iss:25), [interop crash instructions](C:/Users/alexm/source/repos/AetherCore/docs/mcp-setup.md:157), [current instability disclosure](C:/Users/alexm/source/repos/AetherCore/README.md:42), [Godot private reporting](https://github.com/godotengine/godot/security/policy))

Remaining unknowns include fault-injected GPU mutation outcomes, actual physics scratch high-water levels, traffic-budget behavior, Release/Retail/Linux qualification, clean installed-product execution, multi-adapter support, long-session leaks, device-loss handling, broad editor operation completeness and real accessibility workflows. Source review did not certify every render call against ECS isolation or every interop translation unit against runtime dependency rules. No Godot head-to-head stress experiment was run, and Godot documentation does not establish superior power-loss durability for application-specific saves.

The decisive next milestone is a **supported reference product made from delivered bytes**, with its failure cases, operating limits and maintenance obligations written down and repeatable. That turns the existing engine work into a promise another developer can rely on. Broader Godot-like coverage should then grow through the same gates, rather than postponing dependable narrow support until feature counts look similar.
